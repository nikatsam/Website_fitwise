# 4. Detailed remediation items

## UX-001 — Unify verification state across appliance and specialised services

**Severity:** P0  
**Weight:** 10  
**Status:** 🟦 READY FOR RETEST

### Problem

Equivalent checks can expose different certainty depending on the entry page. The specialised Fit Services flow supports a `Needs information` state and source verification for manufacturer-dependent clearances, while dedicated appliance pages may present a green `Fits` state without requiring equivalent verification context.

This creates a trust problem: the same physical situation can be represented with different certainty depending on which Fitwise URL the user entered through.

### Required remediation

Use one shared verification model for all manufacturer/manual-dependent checks.

Required fields when relevant:

- clearance/source status;
- model or manufacturer reference;
- physical dimensions;
- selected/user allowance;
- manufacturer/manual requirement, where applicable.

### Required result logic

1. `✓ Fits` — all hard dimensions pass and required verification data is supplied.
2. `△ Tight` — physical fit passes but at least one selected target fails.
3. `✕ Does not fit` — a hard physical constraint fails.
4. `? Needs information` — the calculation cannot responsibly confirm the requested outcome without required external data.

### Acceptance criteria

- [x] Dedicated appliance pages and Fit Services produce the same state for identical inputs.
- [x] Zero clearance does not silently mean both `verified zero` and `unknown`.
- [x] Unknown manufacturer requirement produces `Needs information`, not unconditional `Fits`.
- [x] Result explains exactly what information is missing.
- [x] Automated parity test covers dedicated vs shared-service routes.

### Retest notes

### Retest — 2026-10-10

**Environment:** Local production build / headless Chrome  
**Build/commit:** Local working tree; no release commit yet  
**Pages:** `/fit-services/`, `/appliances/appliance-install-fit/`, `/appliances/fridge-fit/`, `/appliances/washer-fit/`  
**Result:** All three dedicated appliance routes match the shared appliance mode's state, missing-information message, and dimension rows. Unknown clearance data with zero entered allowance produces `Needs information`; an explicit user-selected zero or a referenced manual treats zero as supplied data and does not conflate it with unknown. Verified-but-short selected targets remain `Tight`.  
**Evidence:** `tests/unit/fit-services.test.ts` (14 passed); `npm run qa:keyboard -- http://127.0.0.1:4322` passed, including route parity checks.

## Page header

- [ ] Visible breadcrumb
- [ ] One clear H1 phrased as the user problem
- [ ] One-sentence explanation of what the calculator checks
- [ ] `Before you start` block
- [ ] Example-data state clearly disclosed

- [ ] Logical numbered sections
- [ ] Plain-language field labels
- [ ] Contextual help for non-obvious measurements
- [ ] Consistent units
- [ ] Optional/advanced fields clearly identified
- [ ] No technical mini-syntax required from ordinary users
- [ ] Accessible names/labels for all controls

## Result

- [ ] One of four official states
- [ ] Plain-language answer first
- [ ] Physical fit vs selected/verified target separated
- [ ] Tightest constraint named
- [ ] Margin/shortfall expressed in user-friendly units
- [ ] Clear next action
- [ ] Full math available but secondary
- [ ] Example result distinguished from user result

## Supporting information

- [ ] Assumptions accessible without dominating the primary workflow
- [ ] Sources/provenance available
- [ ] Methodology linked
- [ ] Relevant next checks only
