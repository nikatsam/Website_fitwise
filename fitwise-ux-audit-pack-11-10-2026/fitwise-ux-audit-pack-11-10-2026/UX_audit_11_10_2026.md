# 5. Detailed remediation items

## UX11-001 — Canonical four-state result model

**Severity:** P0  
**Weight:** 7  
**Status:** 🟦 READY FOR RETEST

### Problem

Newer calculators can produce `? Needs information`, while the global Methodology page and some older calculators still describe only three result states.

### Canonical model

| State                   | Meaning                                                                                 |
| ----------------------- | --------------------------------------------------------------------------------------- |
| ✓ **Fits**              | Hard physical requirements and selected/verified targets pass                           |
| △ **Tight**             | Physical fit passes, but one or more selected targets do not                            |
| ✕ **Does not fit**      | At least one hard physical/access requirement fails                                     |
| ? **Needs information** | Required measurement, source, model, manual or compatibility data has not been verified |

### Required remediation

- Store the result state model in one shared source/module.
- Render the same labels, icons, descriptions and semantics in Methodology and every calculator.
- `Needs information` must not be treated as `Tight` or `Fits`.
- Physical-fit information may still be shown separately when available.

### Acceptance criteria

- [x] Methodology contains all four states.
- [x] Every calculator uses the shared state names/icons and descriptions.
- [x] Missing external verification cannot produce unconditional `Fits`.
- [x] Short state explanation is available beside results without leaving the page.
- [x] Automated tests cover all four states.

## UX11-003 — Replace generated incomplete-state sentence assembly

**Severity:** P0  
**Weight:** 6  
**Status:** 🟦 READY FOR RETEST

### Problem

Incomplete verification messages currently expose generated-string logic, including awkward grammar and double punctuation such as `result..` / `assessment..`.

### Required remediation

Do not concatenate complete error strings into prose. Represent missing information structurally.

Suggested data shape:

```yaml
missingRequirement:
  type: manual_reference
  label: Installation clearance source
  explanation: Installation fit cannot be verified without the exact model requirement.
  action: Add the exact model manual or manufacturer specification.
```

Suggested output:

> **Installation fit isn't confirmed yet.**  
> The appliance physically fits the opening, but its installation clearance has not been verified.  
> **Next:** Add the exact model manual or manufacturer specification, then run the check again.

### Acceptance criteria

- [x] No double punctuation in generated result copy.
- [x] No sentence contains embedded raw error/debug phrasing.
- [x] `Needs information` always tells the user precisely what is missing.
- [x] Every incomplete state has one clear next action.

### Evidence

- Replaced sentence-like `string[]` verification messages with typed requirements (`type`, `label`, `explanation`, `action`) from appliance, monitor-arm, TV mount, hot-tub and play-equipment checks through the shared `FitSummary` and copied report.
- Missing information now renders as a semantic list of specific unverified facts with field-specific actions; the generated explanation is a separate stable sentence and never concatenates complete error strings.
- `tests/unit/fit-summary-copy.test.ts`, `tests/unit/copy-report.test.ts`, `tests/unit/fit-services.test.ts`: 27 tests passed, including punctuation normalization, exact missing requirement/action, escaped rendering and verified-state transition.
- `npm run build`: 73 pages built. `npm run validate:accessibility`: all 73 pages/961 controls passed.
- `npm run qa:keyboard -- http://127.0.0.1:4322`: structured missing information passed on Fit Services, Appliance/Fridge/Washer, Monitor Arm, Hot Tub and Play Equipment; the 41-route keyboard/AX QA also passed.

**Retest note:** Local automated checks only. Production and human copy retests remain pending.

**Weight:** 1  
**Status:** 🟦 READY FOR RETEST

> **✓ Fits exactly**  
> No measurement tolerance remains. Re-check the actual dimensions before relying on this result.

- [x] Exact-fit state comes from the shared result component.
- [x] Every applicable calculator uses the same zero-margin result copy.

- [x] Small nonzero margins remain visibly nonzero in Metric, Imperial and Both displays.

### Evidence

- Added shared margin-aware formatting to result summaries and dimension tables, including the Universal, Dining, Bedroom, Workspace and Fit Services client renderers. A `0.1 mm` margin displays as `0.10 mm` / `0.0039 in` rather than rounding to zero; ordinary-sized margins retain their established formatting.

# 8. Suggested automated QA gates

The remediation should create tests that make future regression difficult.

### Accessibility

- axe-core or equivalent on every calculator route;
- no unlabeled controls;
- no duplicate IDs;
- fieldset/legend or equivalent accessible grouping for related inputs;
- keyboard smoke test for calculator completion.

### UX structure

Assert every calculator template exposes:

- breadcrumb;
- purpose/H1;
- before-start content;
- example-state marker when sample data is loaded;
- result component;
- calculation detail section;
- source/assumption section.

### Result logic

Test:

- fits;
- tight;
- does-not-fit;
- needs-information;
- exact-fit;
- positive/negative floating-point edge cases.

### Content linting

Fail or warn on:

- `..` double punctuation;
- `More assumptions` legacy string;
- obsolete flat-navigation identifiers/classes;
- generic placeholder label such as `Input` when exposed to accessibility tree;
- public helper copy containing internal/debug wording.

   - one core calculator;
